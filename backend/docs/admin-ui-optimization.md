# Chimera 后台界面优化分析

分析日期：2026-10-08。

优化顺序建议为：保护未保存内容 → 修复筛选和批量操作 → 精简用户总表 → 完善设置页反馈 → 完善桌面布局 → 优化加载与维护成本。

初次分析基于现有 HTML、CSS、浏览器脚本和相关管理 API。使用 Node VM、模拟数据及 DOM/API 桩核对了四个逻辑问题，没有连接生产后台或写入业务数据。初次分析时未取得浏览器截图；后续实施使用本机无头 Edge 对本地模拟页面进行了布局和交互检查，结果见下文。尚未测量加载耗时、对比度或读屏体验。

## 首轮实施结果

2026-10-08 已完成以下改动：

- 修复四个已复现的逻辑问题；账户状态与账户类型可以组合筛选，保存隐藏用户草稿不再依赖表格行，删除仅清理目标用户的草稿。
- 设置保存只重填当前模块，保留其他模块的草稿及请求期间产生的新修改；增加保存锁、失败反馈、放弃修改和离开提示。调试 UUID 的重新生成也改为独立草稿，避免随其他模块一起意外发布。
- 用户主表精简为 7 列，固定选择和用户身份列，将资料编辑及历史设备放入原生 dialog 详情面板；显示隐藏选择数量、未保存标记及详情内的保存错误。
- 订阅分组增加权限摘要、启用线路数量及折叠；各设置页使用统一的固定保存栏。
- 安全账户查询改为 UID Map 索引，选择变化不再重建整张用户表。

验证结果：`node --test tests/*.test.mjs` 的 46 项测试全部通过（新增 10 项后台 UI 行为回归测试），类型检查通过，两种 Worker dry-run 均已生成构建产物。全量验证中发现两条原有测试仍断言旧的扁平订阅结构，已对齐当前分组结构，并保留旧 KV 数据迁移的验证。

本机无头 Edge 使用模拟 API 数据验证了用户详情编辑、筛选隐藏草稿保存和跨模块草稿保留，未发现脚本运行错误。桌面截图保存在 `.wrangler/ui-review/`：`users-desktop.png`、`user-details.png`、`subscriptions-desktop.png`。这些交互检查使用本地模拟数据。首轮优化已部署至 `chimera-tiered`，健康接口检查通过。

## 桌面使用调整

根据后续使用要求，后台仅保留电脑使用布局：移除手机菜单按钮、导航抽屉、遮罩和相关事件处理，删除 1200px、760px、480px 的布局断点。页面最小宽度为 1200px，侧栏固定为 220px，用户详情面板固定为 680px；更窄的窗口保留桌面布局并横向滚动，不再切换为手机界面。

验证覆盖桌面交互、1200px 布局，以及小于最小宽度时侧栏保持可见且仍使用多列布局。本次调整只提交 Git，尚未重新部署至 Worker。

后续建议继续处理按模块加载、服务端分页、模块级更新与版本校验，以及更完整的键盘和读屏验证。以下分析保留为初始问题记录和后续优化清单。

## 现有基础

后台包含 11 个模块：用户趋势、流量趋势、占比画像、用户总表、订阅分组、关于页、导航页、注册控制、公告、调试接口、后台登录记录。

已有可复用的基础：深色配色、分组侧栏、表头吸顶、筛选排序、批量操作、CSV 导出、订阅导入预览、错误状态以及部分无障碍属性。图表请求已有请求序号检查，订阅导入已有取消请求和过期结果检查，这些模式适合用于其他模块。

## 第一优先级：修复影响操作正确性的问题

| 问题 | 复现条件与影响 | 优化方案 | 源码位置 |
| --- | --- | --- | --- |
| 保存一个模块会覆盖其他模块的草稿 | 修改公告但不保存，切到关于页保存。`pushSection()` 使用已保存的公告提交，再调用 `fillState()` 重填所有模块，公告草稿被旧值覆盖 | 将已保存状态与各模块草稿分开；保存成功只更新当前模块，保留其他草稿；提供明确的放弃修改操作 | `scripts/settings.client.js:531、768、818` |
| “封禁”筛选始终为空 | 存在封禁用户时选择“封禁”。筛选把 `banned` 与只能为 `formal/guest` 的账户类型比较，所有用户被排除 | 拆成账户状态（全部、正常、封禁）和账户类型（全部、正式、游客）两个筛选；分别判定，支持组合 | `scripts/user-management.client.js:77、92、95`；`document.html:199` |
| 被筛选隐藏的草稿无法保存 | 修改用户 A 后搜索用户 B，点击保存选中修改。A 仍在选择与草稿集合中，但保存函数要求 A 的表格行存在，直接返回失败，没有发出 PATCH | 根据 UID 和草稿构建请求，保存逻辑不依赖可见 DOM；反馈应列出成功、失败与剩余未保存数量 | `scripts/user-management.client.js:308、347` |
| 删除其他用户会清空无关草稿 | 编辑 A，取消选择 A，选择并删除 B。删除检查仅针对 B，但成功后清空所有用户的草稿与未保存集合，A 的修改丢失 | 只移除被删除 UID 的草稿、选择与未保存状态；保留其余用户修改 | `scripts/user-management.client.js:424、434、455` |

这四项在本次模拟检查中分别得到：封禁结果 0 条、隐藏草稿保存发出 0 个请求、无关草稿被清空、公告标题回退到已保存值。属于逻辑复现，仍需浏览器端回归验证。

批量选择还需要显示操作范围。当前筛选变化后保留已选用户，但界面主要显示选择总数。建议显示“已选 12 人，其中 5 人不在当前结果中”，提供清空选择，确认弹窗列出部分用户及影响范围。编辑操作会自动选择用户，确认文案尤其需要解释这一点。

## 第二优先级：提高常用页面的操作效率

### 用户总表

当前主表有 14 列，昵称、品牌、型号、Android 和 App 版本常驻输入框，历史设备内容也嵌入主表。查询和编辑共用一个密集区域，横向定位用户与辨认草稿的成本较高。

建议主表默认显示：选择、用户（昵称与邮箱）、状态、今日流量、本月流量、最后上报、操作。保留表头吸顶，进一步固定选择列与用户身份列。

点击用户打开详情面板，集中展示 UID、设备关系、累计流量和资料编辑。按业务需要保留可选的表格编辑模式。未保存字段使用文字标记配合高亮，不只依靠颜色。

将搜索、账户状态、账户类型、排序放在紧凑工具栏，低频条件收进“更多筛选”；显示已启用的条件和清除入口。批量操作栏在选中用户时出现，突出保存修改和操作范围。

验收：筛选后能保存隐藏用户的草稿；取消选择与修改状态互不混淆；删除其他用户不丢草稿；横向滚动后仍能辨认当前用户。

### 设置页和订阅分组

目前“推送”按钮多在内容底部，`pushSection()` 没有统一的请求中状态、重复提交保护和网络异常捕获。成功提示只有“当前模块已推送”，难以判断保存范围与生效状态。

建议各设置页设置固定操作栏，显示“有未保存修改 / 保存中 / 已保存时间 / 保存失败”，提供保存与放弃修改。按钮文案统一为“保存配置”，需要发布语义时再明确实际生效方式。关闭或刷新页面的离开提示只在有草稿时启用，且不能成为唯一的防丢机制；`beforeunload` 在部分场景并不可靠。[MDN 说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event)

保存流程统一使用 `try/catch/finally` 和提交锁；失败保留草稿，展示可重试提示；字段错误放在对应控件旁，必要时定位到首个错误。请求中编辑需要明确策略：可以暂时禁用当前表单，或保存提交时的快照并保留后续编辑。

订阅分组继续沿用现有折叠线路编辑和导入预览。分组头部显示线路数、启用状态和权限摘要；长列表提供分组折叠、线路搜索与批量启停。导入完成后明确“已加入草稿，尚未保存”，删除草稿中的线路可提供撤销入口。

还有一个保存范围问题：页面看似按模块保存，实际发送整份状态，服务端每次遍历所有启用的外部订阅进行读取或预热。其他模块的保存也可能受订阅处理影响，具体是否访问上游取决于缓存。建议后续支持模块级更新和版本校验，并将订阅处理限制在需要验证的变更上。证据：`scripts/settings.client.js:805`、`routes/admin/state.ts:62`、`services/subscriptions.ts:383`。本次未测量该流程耗时。

### 桌面布局

后台仅面向电脑使用，统一保留桌面侧栏及多列内容区，最小布局宽度为 1200px。手机专用导航和单列样式已移除。

后续布局优化集中在桌面表格、图表和长表单。保留用户身份列、表头和保存栏，避免横向滚动时丢失操作对象，也避免保存栏遮挡最后一个字段。

验收覆盖 1200、1440 CSS 像素视口和桌面窗口缩小，检查导航可访问、多列布局保持稳定，以及长名称不撑破布局。

## 第三优先级：改善信息层级、加载和维护

### 看板与导航

- 用户趋势页目前先显示两张纵向图表，汇总数字位于图表下方。建议顶部显示总用户、所选周期新增、所选周期活跃和统计更新时间，再展示趋势。活跃人数必须沿用周期内去重口径，不能相加日活推算周活或月活。
- 日期控件增加最近 7 天、30 天等快捷范围。比较增长与活跃时可以使用共享范围，也保留按图调整的能力。
- “分组”改为“订阅分组”；将关于页中的版本更新拆成明确的子区或入口，使更新配置更容易找到。
- 侧栏记住展开状态，URL 记录当前模块，刷新与浏览器返回恢复位置。新增总览页前先确认是否确有跨模块查看需求。
- 保留当前深色风格，统一间距、字号、边框和圆角为 CSS 变量；主要动作、次要动作与危险动作使用稳定的样式。优先提高层级和可辨认性，主题切换放在后续。

### 数据与渲染

用户 API 当前返回全部用户；前端每次搜索、筛选、选中都会重建主表。`adminUserSecurity()` 对账户数组反复执行 `find()`，搜索和渲染都会多次调用，数据量扩大时存在近似二次增长的查找成本。证据：`routes/admin/users.ts:41`、`scripts/user-management.client.js:45、77、179、229`。

建议先将安全数据按 UID 建立 Map，预计算搜索文本，选择变化只更新受影响的行与工具栏。之后按真实数据规模增加服务端分页、搜索和排序；分页时明确跨页选择及“导出当前结果”的范围，避免只导出当前页却标成全部结果。虚拟滚动在实测需要时再引入。

登录后会获取注册控制数据、设备画像和三类图表，部分请求属于尚未打开的模块。建议使用模块首次进入加载、缓存与局部刷新；安全数据失败时，允许先显示基础用户信息，同时明确安全相关操作不可用，避免整个用户列表被单个依赖阻断。

抽取统一 API 请求函数，处理鉴权过期、HTTP 错误、网络异常、可配置超时和取消请求。已有的图表请求序号与订阅导入取消逻辑可以复用；超时实现应核对目标浏览器支持。[MDN AbortSignal.timeout](https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal/timeout_static)

后台 HTML、CSS 和 10 个浏览器脚本的源文件共 223,420 字节，通过 `admin-ui.ts` 拼成单个页面；这个数字不代表压缩后的网络传输大小。可先梳理旧用户表、安全页面等当前没有导航入口的代码，再按实测决定是否拆分资产。现阶段可以在原生 JS 上完成上述优化，优先把草稿状态和 API 处理收敛清楚。

### 键盘与语义

侧栏采用 `tablist/tab/tabpanel`，当前页签只处理点击和 `aria-selected`，未实现垂直页签的方向键、焦点管理和完整面板关联。可以改成具有当前页状态的普通模块导航，或按完整页签模式补齐行为。不能只补角色属性。[W3C Tabs Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)

统一可见的键盘焦点样式，检查弹窗关闭后的焦点恢复、状态通知、表格选择控件的用户名称及错误字段标识。颜色对比度和读屏结果需要实际页面测试，本次不作合规判断。

## 建议实施顺序与验证

1. **操作正确性**：修复四个已复现问题，明确跨筛选选择范围；为这些问题添加行为回归测试。
2. **常用页面**：重排用户表与详情编辑，增加设置页保存状态和固定操作栏。
3. **布局和导航**：保持桌面侧栏，统一页面头部、筛选与操作样式，恢复模块位置。
4. **数据与维护**：建立 UID 索引、减少整表重渲染、按模块加载，再根据实测引入分页与资产拆分。

浏览器回归重点包括：跨模块保存、筛选隐藏草稿、跨结果选择、局部删除、重复提交、断网失败、较大数据列表、桌面布局和键盘操作。性能需要分别测量接口响应、渲染与搜索响应，不能用代码规模替代测量。

第一阶段及用户总表、订阅分组的首轮优化已完成。下一步建议优先处理按模块加载与服务端分页。
